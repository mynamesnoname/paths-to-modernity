# REQ-009 — 完成可用的光谱知识图谱与 ontology

2026-10-13 用户要求：“请调整或新增本项目的plan，补全实现ontology的最后gap”。本需求承接同轮代码审查，而不是把既有计划的完成声明当作端到端图谱已完成的证据。

## 当前事实与目标

- 版本化 registry 已有谱线、类别、规则及三态求值；运行时的 Evidence Graph 默认关闭，生产构图目前只写入光谱、连续谱、CWT 特征、Redrock 拟合。`HypothesisNode`、`ClaimNode`、`QualityIssueNode`、`LineIdentityNode` 已定义，但生产构图未创建它们。
- SH/HS/RA 的形式规则结果主要保存在分析字段或独立 JSON；部分输入只定位到 CSV 行或审计字段，无法稳定沿图查询到观测和最后的审计结论。论证 evaluator 有离线实现，不能据此声称已驱动主流程。
- 目标是让一次运行的最终结论可以机器查询并人工复核：结论 → 审计/规则 → 假设与谱线主张 → Redrock 拟合、CWT/窗口观测及原始产物；每个跳点要说明来源、版本、未知与冲突。

## 边界决定

1. 保持现有 Python 类型化 registry 与 Evidence Graph 作为首要运行时表示。RDF/OWL、SHACL、SPARQL 或图数据库不是“可用”的先决条件；如果将来需要跨系统互操作，再以可验证映射或导出单独决策。
2. 图须区分确定性测量、模型主张、形式规则结果和人工/模型审计；不把来源文件行号或模型文本伪装成原始观测节点。节点与边的版本迁移、稳定身份和可重放性必须保留。
3. `NOT_FOUND` 是观测。未知、局部掩膜、范围外、未核验及歧义输入不自动成为负证据。特定物理关系（如 [O III] 配对）必须引用自己的证据；`rule:formal-qso1-missing-broad-line` 的致命资格需按这一原则复核。
4. 规则可以提示、约束或纠正代理输出，但每一种作用要在 trace 中可辨认；不得把事后附加 caveat 说成曾指导前面的模型选择。
5. 离线夹具验证机制；正式“可用”还需真实 FITS/Redrock/LLM 的保存图、端到端查询、对照运行和独立带标注样本的评估。不得用合成夹具或一次模型输出替代科学验证。

## 组织

`ST-012` 管总体闭环；`WP-035` 补生产结论节点，`WP-036` 补图约束、规则/证据查询和决策作用记录，既有 `WP-031` 专管缺线链，`WP-037` 做真实贯通验收。`WP-012` 的独立缺陷评级校准仍保留其原有责任边界。
