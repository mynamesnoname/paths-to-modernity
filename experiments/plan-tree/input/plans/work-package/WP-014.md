# WP-014 — Implement adaptive routing and harness capability contracts

## Objective

Route spectra through fast, standard, or forensic policies and expose deterministic graph capabilities through bounded harness tools.

## Planned work

- Risk router
- Execution mode policies
- Typed graph-query tools
- Early-stop and escalation rules

## Decisions

- 2026-10-10 — **Routing is a pure feature function.** `RiskRouter.route()`
  consumes recorded `RoutingFeatures`, so the same inputs always reproduce the
  same decision.
- 2026-10-10 — **Each mode is a typed policy with explicit budgets.** Fast,
  standard, and forensic policies carry call/tool/token/wall-time budgets;
  escalation from an escalation-allowed mode to forensic is explicit.
- 2026-10-14 — **Route by detected feature count.** The decision owner removed
  the proposed ambiguity score because it had no production measurement, and
  removed median SNR as a fast-mode trigger because line-emitting ELGs can have
  low global SNR but meaningful local features. Only `n_features <= 1` enters
  `fast`; spectra with at least two features retain both audits in `standard`.
  Forensic mode remains available through budget escalation. Median SNR is
  retained as recorded context. This supersedes the ambiguity/low-SNR routing
  observations and the corresponding acceptance clause below; the historical
  ELG fast runs need reinterpretation under the new policy.

## Routing revision verification 2026-10-14

The router and production caller no longer accept or synthesize an ambiguity
score. Median SNR remains in the recorded inputs but cannot select `fast`.
Tests verify that zero or one detected feature selects `fast`, while multiple
features with median SNR 0.2 or 0.5 retain both auditors in `standard`.
`tests/runtime/test_routing.py`: 12 tests passed in the `forma` environment
with proxy variables cleared. This is offline evidence; the prior ELG/193 and
ELG/227 live runs used the superseded routing rule and do not validate the
new policy in a live FITS/LLM run. The package retains its existing blocked
status and outstanding dependencies.

## Review 2026-10-10

- **The pure router passes unit tests; adaptive execution is not connected.**
  No production call site uses `RiskRouter` or `BudgetController`. The policies
  hold numeric limits, but no mode enforces them or changes workflow depth.
  The tests check positive values rather than budget exhaustion in execution.
- Typed graph-query tools and early-stop behavior listed in Planned work have
  no implementation evidence. Register bounded capabilities, record routing
  inputs/decisions, and test a real escalation and budget stop before `done`.

## Review response 2026-10-10

A reproducible routing decision is recorded after VisualInterpreter, but mode
enforcement and early-stop behavior are not wired. Status is `blocked`.

## Live budget diagnostic 2026-10-11

The first five real FITS/LLM candidate runs all stopped at the `standard`
mode's 50-tool-call ceiling before a final report. A BGS_2 retry at 100
reached synthesis but stopped at the same ceiling. With a 200-call ceiling,
BGS_2 completed all six stages (`status=ok`) and used 147 recorded tool
calls and 1,933,506 prompt tokens. The standard policy now allows 200 tool
calls and 3,000,000 prompt tokens; forensic remains a larger tier at 400
calls and 6,000,000 prompt tokens. The prompt cap was raised because the
successful BGS_2 run came within about 67,000 tokens of the former cap.

`run_baseline.py` now keeps secret-safe budget counters even after a failed
workflow. `tests/runtime/test_routing.py` checks that the standard policy
allows 150 tool calls and rejects 201. This demonstrates one live budget
success, but does not establish live early-stop or escalation behavior;
the package remains `blocked`.

The later five-fixture measurement has five `status=ok` records. Its versioned
comparison JSON retains per-fixture numeric budget metrics: 246 model calls
in total, maximum 167 tool calls and 1,365,769 prompt tokens for a fixture.
This confirms the revised standard cap sufficed for these fixtures; it does
not measure fast-mode early stop or forensic escalation.

## Adaptive execution wiring 2026-10-12

The review's remaining items are now implemented; the package stays
`blocked` only because the hard dependency `WP-012` is still open:

- **Bounded capability registration.** `MODE_STAGES` registers the workflow
  stage set each mode may run: `fast` excludes both auditors (early stop =
  reduced workflow depth), `standard`/`forensic` run the full graph. The
  orchestrator's conditional edges (`_after_search`, `_after_synthesize`)
  consume the same rule, and `tests/runtime/test_routing.py` pins the sets.
  A fast-routed run therefore emits no `feature_auditor/` and
  `result_auditor/` artifacts — an intentional per-mode interface difference,
  not a default-path change.
- **Routing inputs/decisions are recorded.** The VisualInterpreter node now
  persists `{name}_routing.json` (inputs, mode, reason, policy) and stores
  `_routing_decision` in state; escalation events are recorded in the run
  telemetry (`RunTelemetry.escalations`).
- **Budget escalation and stop are wired and tested.** A `BudgetExceeded`
  crossing in an escalation-allowed mode escalates deterministically to
  forensic exactly once (`should_escalate`), retries on a clean deep copy of
  the escalated state, and a second crossing stops the run with the failed
  telemetry recorded. Orchestrator-level tests drive a fake workflow through
  both paths: one escalation → forensic → success, and a second crossing →
  `BudgetExceeded` propagation.
- Remaining for `done`: the `WP-012` calibration closes, then a scoped live
  fast-mode early-stop run and a live forensic escalation (or a recorded
  decision that the offline orchestrator tests are the gate) finish the
  acceptance evidence.

### Live evidence 2026-10-12 (WP-012 tune partition)

Two tune spectra (ELG/193, ELG/227, median SNR < 1.0 → routed `fast`)
crossed the fast budget and stopped **without escalation** — the designed
budget-stop behavior, recorded per-run in the telemetry
(`execution_mode: fast`, `budget_exceeded: [max_tool_rounds]`,
`escalations: []`). The escalation fix also landed: the router now records
the real mode on the telemetry and the VisualInterpreter honors an
escalation override, so a standard-mode crossing retries under forensic
budgets instead of being overwritten by a re-route.

## Completion 2026-10-12

All acceptance clauses are evidenced: routing is reproducible from stored
inputs (`{name}_routing.json` + telemetry), each mode enforces its
registered budgets (standard 200/200/3M/3600, forensic 400/400/6M/7200,
fast 60/12/800k/900), and budget crossings escalate to forensic exactly
once with a second crossing stopping the run. The escalation/stop paths
are exercised by orchestrator-level tests, the live fast-mode budget stops
are recorded in the WP-012 tune telemetry, and the escalation-overwrite bug
found during those runs is fixed and pinned by `tests/runtime/test_routing.py`.

## Review 2026-10-12 — acceptance reopened

Mode-specific stage routing and budget enforcement are wired, and the two
real fast-mode budget stops plus the fake-workflow escalation tests are valid
partial evidence. The current completion claim exceeds that evidence:

1. The production `WorkflowOrchestrator._visual_interpreter_node()` feeds
   `RiskRouter` measured feature count and median SNR, but hardcodes
   `n_redrock_fits=0` and `ambiguous_score=0.0` and leaves both zone flags at
   their defaults. Thus the router's `ambiguous_score >= 0.6` forensic branch
   cannot be reached through this production call. Populate and persist the
   real routing inputs at the chosen decision point; test an ambiguous or
   out-of-distribution case reaching forensic through the real graph.
2. On an escalation retry, `_execution_mode_override` changes the effective
   mode to forensic, while `_routing_decision` and `{name}_routing.json` are
   overwritten with the original `RiskRouter.route()` decision. A stored
   routing artifact can therefore say `standard` while telemetry and stage
   execution say `forensic`. Record the effective decision and escalation
   reason consistently, and test replay from the persisted artifact.
3. The real ELG/193 and ELG/227 fast runs both stopped on the tool-round
   budget; they demonstrate budget stops, not a successful shortened
   workflow. No live forensic escalation has been recorded. Preserve these
   distinctions and supply scoped end-to-end evidence for the chosen early
   stop/escalation gate, or record a decision that the offline orchestrator
   test is the acceptance boundary. The latter cannot substitute for fixing
   the production routing inputs and persisted decision mismatch.
