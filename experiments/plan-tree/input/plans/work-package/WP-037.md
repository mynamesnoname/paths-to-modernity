# WP-037 — Real-workflow acceptance

## Objective

Demonstrate that the complete graph is usable and does not misstate the scientific evidence in actual analyses.

## Planned work

- Freeze code, ontology/config versions, inputs and model settings; run representative FITS through the Redrock and LLM pipeline with graph enabled and preserve an anonymized, replayable provenance record.
- Query selected, rejected, revised and unknown cases from the saved graph. Audit broken or ambiguous links and rule effects, including the context-specific missing-line rule.
- Compare graph-on with the accepted baseline using the established stochastic comparison policy; record wall time, model calls and graph build/serialization cost.
- Use independent labels for classification/redshift error analysis, including abstentions and failures. Check that the saved graph represents the reported defect rating or null reason and its provenance accurately; independent grade-severity agreement remains with `WP-012`. State limits of sample size and model variation.

## Decisions

- This is the release gate for the stronger claim “usable knowledge graph + ontology”; schema/unit tests establish components only.
- Do not rerun LLM work as part of planning. Runtime execution and costs are part of this future work package.
- 2026-10-15 — The decision owner deferred `WP-012`'s independent defect-severity assessment. This package accepts the real graph chain and independent classification/redshift comparison separately; it makes no claim that HIGH/MEDIUM/LOW have been independently validated. Finish `WP-040` before freezing the code and effective parameters for the graph-on/off comparison.

## Completion

- Planned. `WP-031`, `WP-035`, and `WP-036` are done; `WP-040` remains the hard prerequisite before this acceptance run starts. The prior diagnostic FITS runs below do not constitute the full graph-on/off and independent-label gate.

## Root cause of the `ELG/3` contradiction, 2026-10-15 (traced)

The earlier note in this node grouped `ELG/3` with the Feature-Auditor empty-matrix
condition. Tracing it shows a **different and more specific defect**: a missing
verdict field that three consumers resolve in opposite directions, while the
judgement the auditor actually recorded is read by nothing.

- `feature_auditor/verdict.json` holds 13 `feature_verdicts` rows with keys
  `{wl_obs, feature_type, is_real, detection_reliability, issues}` — **no
  `recommendation`** — and `is_real` is true for 11 of them. The skill requires
  both fields (`skills/AnalysisAuditor/feature_audit_skill.md:289-322`).
- `harness/hypothesis_synthesis.py:116-122` reads `recommendation` and keeps
  anything it does not recognise, so the synthesis prompt and report state
  `KEEP = 13, FLAG = 0, REMOVE = 0` — the row count, not a judgement.
- `harness/hypothesis_synthesis.py:196-197` reads the same field and requires
  `KEEP`/`FLAG`, so the same 13 rows are all dropped: the verified contradiction
  matrix is empty, the synthesis has no candidate, and the run records
  `no_candidate` while its own table lists `H1 0.1413` (equal to the VI redshift)
  as `SUPPORTED (harness)` with 7 LIKELY lines.
- `AnalysisAuditor.py:1487-1500` writes the cleaned CSVs' `feature_audit` column
  from the same field and defaults to `KEEP` (22 rows marked KEEP here).
- `grep -rn "is_real" --include=*.py src/FORMA` returns **zero hits**: the field
  the auditor actually produced cannot influence any decision.

Nothing validates the verdict rows against their schema; the only structural check
counts `{"wl_obs"` blocks to detect truncation (`AnalysisAuditor.py:98-128`), so a
schema-incomplete row set flows straight through. Blast radius measured over the
challenge cohort: `ELG/3` is the **only** run of 16 whose rows lack
`recommendation` (0/13; every other run has it on every row), so this is a one-off
schema dropout rather than a property of the new SH rules — but it silently cost a
legacy-rated `MEDIUM` spectrum its rating, and the disagreement surfaces as two
contradictory numbers rather than an error.

The other abstentions in that cohort are not this defect: `BGS/32` (0 of 8 rows
judged real), `QSO/6` (1 of 16) and `LRG/9` (none kept) follow the auditor's own
verdicts, and `QSO/5` is a synthesis override of a harness-supported hypothesis
that still needs its own trace.

### How `verdict.json` is produced, and where `recommendation` actually appears

`_run_llm_agent` (`AnalysisAuditor.py:1511+`) streams the agent's messages into
`feature_auditor/stream.md`, then concatenates **only the AI messages** and calls
`_extract_json_block(raw_content, keys=["feature_verdicts"])`
(`AnalysisAuditor.py:168-190`), which returns the **first** ```json fence in that
text (falling back to a shallow bare `{...}` that cannot match nested row objects),
and `json.dump`s the result to `verdict.json`. The only checks are that the parse
succeeded, that `feature_verdicts` is non-empty, and the truncation heuristic that
counts `{"wl_obs"` blocks; **no per-row key is validated or normalised**.

Checked against the stream for `ELG/3`, which holds 22 fenced blocks: the six
`"recommendation"` occurrences (offsets 28552-30765) all lie inside the
`<details>System Prompt</details>` section — they are the skill's own Step-8 example
(`skills/AnalysisAuditor/feature_audit_skill.md:289-322`). The model's final answer
(offset 226171) contains **zero**. So the field exists in the prompt's example and
nowhere in the model's output; `verdict.json` is a faithful copy of that answer, and
the defect is the absent validation, not the extraction. (A related fragility, not
triggered here: the first AI-content fence wins, so an example JSON written early in
the model's own message would be parsed instead of its verdict.)

## Implemented 2026-10-15: validated verdict writes (FA + Result Auditor)

The decision owner's ruling was to stop scraping the verdict out of prose and let
a tool own it, with a **strict** per-row contract, a **flagged** fallback, and one
shared validator for both auditor stages. Implemented as:

- `harness/verdict_io.py` — one schema and one accessor:
  `validate_feature_verdict` (every row needs `wl_obs`, `feature_type`, `is_real`,
  `detection_reliability`, `issues`, `recommendation` ∈ KEEP/FLAG/REMOVE),
  `validate_result_verdict` (`verdict` ∈ CONFIRM/NEEDS_REVISION/UNCERTAIN;
  `calibrated_confidence` ∈ HIGH/MEDIUM/LOW/null with a **required** reason code
  when null; every `line_revisions` entry needs `line` and `action`),
  `write_verdict`, `load_verdict`, `provenance_of`, and `row_recommendation` — the
  single reading of a row's decision.
- `write_feature_verdict` and `write_result_verdict` tools: refused writes name the
  offending rows/fields and write **nothing**, so the verdict on disk is either
  absent or valid. Each artifact records `_written_by`
  (`write_*`/`fallback_regex`), and a wrong `file_path` is refused with the correct
  path. Both stages now retry up to three times with the validator's problems fed
  back as a repair request; the FeatureAuditor's sentinel is now "no schema-valid
  verdict" rather than "could not parse JSON".
- Consumers agree by construction: the synthesis summary buckets a row by
  `row_recommendation` into KEEP/FLAG/REMOVE/**UNCLASSIFIED** (reported, never
  counted as KEEP), the verified-matrix filter **keeps** a feature whose decision it
  cannot read and records `decision_problem` on the row, the cleaned CSV uses the
  projection's vocabulary through `cleaned_csv_audit` (no `else → KEEP`), and the
  dead `_clean_rec` helpers whose opposite defaults caused the contradiction are
  gone.
- Prompts: `feature_audit_skill.md` and `result_auditor_skill.md` now require the
  tool call, the run messages carry the exact verdict path, and the prompt-authority
  audit was regenerated (71 statements, 0 problems). `docs/graphs/FA/FA规则.md` and
  `docs/graphs/RA/RA规则.md` were updated where they described the old delivery and
  the old "one LLM call, no retry loop" behaviour.

**Verified end to end on the spectrum that failed.** `ELG/3` re-run with the new
code: the FeatureAuditor wrote 10 rows through `write_feature_verdict`
(4 KEEP, 3 FLAG, 3 REMOVE, **0 unclassified**), the analysis auditor wrote through
`write_result_verdict`, and the run records `MEDIUM` where the 2026-10-15 run had
recorded `no_candidate`. Tests: `tests/reasoning/test_verdict_io.py` (20 tests:
refusal names the rows, nothing is written on refusal, provenance is visible, the
legacy shape no longer loads, the null-confidence contract, and the two consumer
surfaces agree for every decision).

## `QSO/5` traced 2026-10-15 — a justified abstention, not a defect

The challenge cohort's remaining unexplained abstention is explained, and it is
correct behaviour. After the auditor's own filtering exactly **one** unambiguous
feature survives (a broad emission hump at 4179.2 Å, FWHM 5500-6100 km/s), and it
is claimed by two mutually exclusive hypotheses: `H1 = C IV` at z=1.7057 and
`H3 = C III]` at z=1.2145. Neither gains a second line — H1's required C III]
counterpart at 5151 Å was REMOVED as a continuum-slope artifact and its Mg II is a
single-pixel spike; H3's [Ne V] is absent and its Mg II is NOT_FOUND. The synthesis
report states the reason itself: per `rule:formal-line-inventory` a single LIKELY
line cannot be distinguished from a chance alignment, so it overrides the harness's
per-hypothesis "supported" flag and records `no_candidate` with
`verdict=UNCERTAIN`, `redshift=null`.

The legacy pipeline rated this spectrum `LOW`. The difference is therefore a
**policy** difference (publish a LOW rating for a single-line degeneracy, or
abstain), not a regression; if the decision owner prefers the more informative
rating, the place to change is the zero-confidence band of
`rule:formal-line-inventory`, not this pipeline path.

## `BGS/80` reproduced 2026-10-15 — an empty audit matrix is fatal

Reproduced with the current code (diagnostic run, `.data/runs/diag-bgs80`, not a
boundary measurement). The chain:

- The CWT stage detects only **3 peaks and 0 troughs** in the whole spectrum; all
  6 harness hypotheses consequently adopt **nothing** (every catalog is
  NOT_FOUND/MASKED, 17-27 rows each). Their reports give the reason: the three CWT
  features sit 73-447 Å from every predicted position, beyond the 80 Å rejection
  bound, and the targeted fits recover no signal.
- The FeatureAuditor's contradiction matrix is built from LIKELY/MARGINAL rows, so
  it is empty and the stage records
  `{"skipped": true, "reason": "No LIKELY or MARGINAL features to verify."}`
  (`AnalysisAuditor.py:1759`).
- `HypothesisAnalyst.run_hypothesis_synthesis` treats **any** skip as fatal
  (`HypothesisAnalyst.py:136-166`): it writes the honest abstention record
  (`verdict=UNKNOWN`, `confidence=null`,
  `confidence_unavailable_reason=auditor_not_run`) and then raises
  `FeatureAuditorFailed`, which aborts the workflow.

The run therefore exits non-zero with no auditor verdict, no report, no evidence
graph and no `in_brief` row — only `80_hypothesis_analysis.txt` and the spectrum
figures survive. **The abstention is already computed and then thrown away**, and
"nothing to verify" is not a malfunction: it should end the run as an abstention
(the record the code already writes) rather than as a failure. This is the same
condition that silently produced `no_candidate` on `ELG/3` before the verdict
repair, seen from its other, destructive side.

## Fixed 2026-10-15: an empty audit matrix no longer kills the run

Decision owner's instruction: make `BGS/80` behave. Implemented as a distinction
between two conditions that share one `skipped` sentinel:

- `AnalysisAuditor` now labels its sentinels: an empty verified matrix carries
  `skip_code="no_verifiable_features"`, an exhausted schema/parse loop carries
  `skip_code="auditor_failed"` (`AnalysisAuditor.py:65-66`).
- `HypothesisAnalyst.feature_audit_abstains()` reads that label in the **positive**
  form — only an explicit empty matrix abstains, so a broken audit or an older
  sentinel without a code can never be mistaken for a quiet result.
- On abstention the stage writes the record the contract wants
  (`verdict=UNKNOWN`, `redshift=null`, `confidence=null`,
  `confidence_unavailable_reason="no_candidate"`, the FA reason in `caveats`) and
  **returns**, letting the run continue into the analysis auditor's `redshift is
  None` guard, the report writer and the graph projection. Any other skip keeps
  the previous fatal behaviour.
- `no_candidate` replaces `auditor_not_run` on this path: the audit *did* run and
  found nothing to verify; what is missing is a selected candidate. The analysis
  auditor's guard writes the same code, so the two stages agree.

## Degenerate single-hypothesis output inflates the synthesis prompt, 2026-10-15

Observed while smoke-testing an unrelated change on `BGS/13`
(`.data/runs/cahk-smoke`, diagnostic): the run stopped on
`budget exceeded: max_prompt_tokens` (3.66 M against 3 M) after 1304 s. The cause
is not the change under test — it is a degenerate model response:

- One harness hypothesis (`H2`) collapsed into a repetition loop: its stream holds
  94,094 lines but only **409 unique** ones ("OK." ×31,219, "Let me go." ×24,988,
  "Let me write the tool calls." ×12,488), 1.37 MB of filler with **no tool results
  and no `2_report.md`**. The blob contains zero mentions of the knob under test,
  and the other five hypotheses stayed at 34-71 KB, so this is model collapse, not
  a reaction to a prompt number.
- That filler is embedded **verbatim** in the synthesis user message, so the
  stage's prompt grew from 122 KB to 1.46 MB. The synthesis agent then re-sends
  that prompt on every turn, which is what exhausted the prompt-token budget.

So a single malformed hypothesis can multiply the cost of the remaining stages by
an order of magnitude, and nothing detects or caps it. Two guards would close it,
and they are independent: (a) detect degenerate output at the harness boundary
(unique-line ratio and/or a size ceiling) and record that hypothesis as a harness
failure with a reason, and (b) cap the per-hypothesis reasoning the synthesis
prompt embeds, with the truncation stated in the prompt. The feature auditor of
the same run was unaffected (24 rows written through `write_feature_verdict` with
11 KEEP / 3 FLAG / 10 REMOVE).

## Stage-6 diagnosis, 2026-10-16: the report agent may finish without writing the report

Three of the five graph-on fixtures aborted with `Report Writer returned no final report
document` (ELG_6, QSO_116, QSO_4); BGS_2 and LRG_1 completed. Stages 1-5 finished normally
in every case (QSO_116 even had a written RA verdict, `CONFIRM | MEDIUM | marginal`), so the
failure is confined to the report stage.

**Evidence, from the two report streams:**

| Run | LLM turns | `### Tool Call: write_report` | `final_report.md` | Outcome |
|---|---|---|---|---|
| BGS_2 | 3 | present | written | exit 0 |
| QSO_116 | 2 | **absent** | missing | exit 1 |

In QSO_116 the stream's last message is an AI preamble — "Lyα … gives σ_z = 0.000658. Now
writing the report." — with **no tool call**, so the ReAct loop terminated normally and the
required side effect never happened. `write_report` appears in that stream only in the system
prompt and the user instruction, never as a call.

**Why the existing repair path does not catch it.** The stage's only recovery is
`_complete_pending_tool_turns` (`harness/result_auditor.py`), which resumes the agent *only
when the last message is a tool message*:

```python
if not pending or getattr(pending[-1], "type", None) != "tool":
    break
```

A final AI message without a tool call breaks the loop immediately, so "the model announced
the report and stopped" has no repair. The other four stages use `run_continuation_*`
machinery for exactly this class of incomplete turn; the report stage does not.

**Not the earlier blocker.** Budgets were not exhausted (`max_turns = 30` with 2 turns used;
no `budget exceeded` line), so this is a distinct defect, and it is intermittent — the model
chooses whether to call the tool — which is why 2 of 5 passed.

**Options (no decision taken).** (1) Extend the repair path: when the loop ends and no
document exists, re-prompt the agent a bounded number of times with an explicit instruction to
call `write_report` now; (2) accept a final AI message that *is* the report (already partly
supported by the `# Final Analysis Report` check) — it does not cover this case, where no
report text exists at all; (3) degrade instead of abort: record a declared reason code and
return all artifacts with an empty `in_brief` rather than raising, so the run is measured as a
bounded gap (the blocker's "abstention instead of abort" idea).

Recommendation: (1) plus (3), then re-run only the affected fixtures. Until then the graph
chain cannot be accepted on these five fixtures, because a run without a final report has no
output contract or final-decision provenance to check.

## Fix implemented 2026-10-16 (option 1: bounded document repair)

Decision owner: implement option 1 only; option 3 (degrade instead of abort) is **not**
implemented, so a run that still cannot produce a report continues to abort as before.

- `harness/result_auditor.py` gains `_repair_missing_report()`, called in `arun` right after
  `_complete_pending_tool_turns`, with the new `max_document_repairs: int = 2` parameter.
- It fires only when the report is absent — neither a non-empty `final_report.md` nor a final
  message starting with `# Final Analysis Report` — and only for a turn that ended by itself:
  a last message of type `tool`, or a pending tool call, is left to
  `_complete_pending_tool_turns`. A run that already wrote its report is untouched
  (`agent.ainvoke` is not called again).
- The re-prompt names the tool and the path and forbids prose: *"You did not write the
  report. Call the tool now: write_report(file_path=…, content=<the complete report
  markdown>) … Do not reply with prose, do not summarise what you are about to write, and do
  not ask for confirmation."* Each attempt is logged with its index and bound.
- Tests: `tests/reasoning/test_report_writer_repair.py` (6) — a written report is never
  re-prompted, a preamble-ending turn is repaired and the instruction names `write_report`,
  the repair stops at its bound without looping, an unfinished tool turn is not treated as a
  missing report, a report in the final message counts as written, and an empty report file
  does not count. Suites: 806 tests, the only failure being the regenerated pinned record.
- Verification on real spectra is queued: `ELG_6`, `QSO_116` and `QSO_4` re-run with
  `EVIDENCE_GRAPH=true` into `.data/runs/wp037/graph-on-rerun/`, after the current sweep ends
  so runs stay sequential. `.data/runs/wp037/rerun_driver.log` records, per fixture, whether
  the repair fired (count of the re-prompt log line) and whether `final_report.md` exists.
- Note on the sweep: each fixture is a fresh `scripts/main.py` process, so graph-off fixtures
  started after this fix ran with it, while the three graph-on failures predate it.

## Why the result auditor never ran for `QSO_4` (graph-on), 2026-10-16

Traced from `.data/runs/wp037/graph-on/QSO_4.log` (timeline 03:44–03:46):

1. Stages 1–3 completed normally (the FeatureAuditor wrote 23 verdict rows: 5 KEEP / 9
   FLAG / 9 REMOVE). Hypothesis 4 then collapsed into a repetition loop ("let me do it"
   filler, 1,245 KB stream, 257 unique lines), observed by the decision owner.
2. Stage 4 (synthesis) embeds each hypothesis stream verbatim, so the prompt grew past the
   standard **3 M token** cap; at the next node boundary the run crossed the budget.
3. `WorkflowOrchestrator` caught `BudgetExceeded` and, because standard allows escalation,
   switched the budget policy to **forensic (6 M)** and retried (`attempt 1/3`, `2/3`).
   **The telemetry counters are cumulative and are not reset by escalation or retry** —
   only the cap changes — so each retry re-entered Stage 1 with the counter already spent
   and died again within seconds at the first node boundary.
4. The final attempt aborted: `Failed to process image QSO_4.fits: budget exceeded:
   max_prompt_tokens` — **before Stage 5 (analysis auditor) and Stage 6 (report writer)**,
   hence no `result_auditor/` and no `report_writer/` directory.

So the auditor was not skipped by any mode/stage-set policy (standard and forensic both
list it): it was **starved by a run-wide cumulative budget** that one degenerate hypothesis
consumed. The stage whose job is to rate exactly such a hypothesis was the casualty. The
same fixture's graph-off run completed (13,813-byte report) because the collapse is
stochastic, not fixture-inherent.

**Design questions this raises (decision owner):** whether budget counters should reset per
attempt (they currently survive escalation/retry); whether the synthesis prompt should be
bounded at the source (the degenerate-output guards); and whether an abort before the
auditor should record the failure reason and preserve Stages 1–4 instead of retrying into
the same wall.

## Decisions implemented 2026-10-16 (budget accounting and termination records)

Decision owner's rulings: (1) escalation/retry **resets** the consumption counters;
(2) **no** degenerate-output guards for the model's stochastic collapse loops; (3) a
terminated run records a structured outcome whose `status` names the stage it reached.

Implemented:

- `RunTelemetry.reset_consumption()` zeroes `model_calls`/`prompt_tokens`/
  `completion_tokens`/`tool_rounds` and opens a fresh budget window
  (`budget_started_at`); `_check_budget` measures wall time from that window. The
  escalation branch and both retry branches (connection, timeout) call it before the
  re-run, so a retried attempt starts against an unspent cap instead of the previous
  attempt's counters. This is the change that would have let the `QSO_4` escalation
  actually run under forensic instead of dying at the first node boundary.
- Structured termination record: `_write_termination_outcome` writes
  `run_outcome.json` into the run directory on every final termination path (budget
  exhaustion, cancellation, generic failure). `status` is `terminated_in_<code>` with
  codes `VI`/`SH`/`FA`/`HS`/`RA`/`RW` from `STAGE_CODES` (the stage marker is set in
  `_tracked_stage` before the node runs and cleared at the start of
  `_run_analysis_single_frozen`), plus `reached_stage`, `reason`, `attempt`,
  `execution_mode`, the frozen-parameters digest and a budget snapshot (caps and
  consumed counters). Advisory: a write failure never changes the outcome.
- Tests: `tests/runtime/test_run_outcome.py` (4): stage codes incl. `terminated_in_SH`,
  document shape (stage, reason, caps, consumed, attempt), counter reset, and the
  `terminated_in_FA` record round-trip. Suites: 810 pass.
- Explicitly **declined by the decision owner**: degenerate-output guards (detect/record +
  cap embedded reasoning) — the stochastic collapse loops are accepted as-is; a run they
  kill now ends with a `run_outcome.json` (`terminated_in_HS` / `terminated_in_SH` as the
  case may be) instead of only `exit=1` and a log line.

## QSO_4 [Ne V] classification investigation, 2026-10-16

The selected H4 is **not** where the Galaxy label first appeared. Its
`single_hypothesis/4_report.md` recorded [Ne V] 3426 at 4242.4 Å as LIKELY
and called the z≈0.238 solution AGN/QSO, although it incorrectly suggested
Type 1 from Balmer widths of only 631–755 km/s. In the graph-on rerun FA
recorded that feature as `is_real=true`, `recommendation=FLAG`, reliability
medium. HS then interpreted the same FLAG as a non-convincing AGN indicator,
chose `Galaxy`, and RA wrote `audited_class=ELG`, `nev_convincing=false`,
removing [Ne V]. In graph-off, FA instead recorded `KEEP`/high reliability
and HS chose QSO. One run per mode cannot attribute the difference to graph
execution rather than model variability.

The saved NPZ gives a concrete check on the graph-on FA rationale: within
4141–4341 Å, the 4242.4 Å peak has flux 11.83 on a local continuum near 7.2,
single-pixel IVAR uncertainty ≈0.23 and prominence 5.38; the next measured
local prominence is ≈1.22. The peak spans multiple pixels and matches the
predicted [Ne V] wavelength within 0.8 Å. This does not prove its astrophysical
identity, but the archived statement that it is one of several comparable
bumps is not supported by this window's numbers.

The prompt failure was a circular class filter in HS: its old Phase 3 text
asked the agent to prune AGN lines that conflict with a provisional Galaxy
class and to keep only visually dominant AGN lines; Phase 4 required prominent
AGN features and defaulted ambiguous cases to Galaxy. Another sentence
incorrectly treated no broad line as excluding every QSO, ignoring Type 2.
RA likewise treated low-amplitude narrow [Ne V] in a Galaxy-labeled catalog as
evidence of an FA artifact. The FA neighborhood instruction did not require
named comparator peaks, allowing an unsupported “several comparable wiggles”
claim. The single-hypothesis prompt did not prevent the Type 1 subtype error.

The HS, RA, FA and single-hypothesis skills, classification KB, ionization KB
and HS/RA rule summaries were corrected. They now separate observed-feature
reality, line identity and class; keep a real FLAGged line as weakened rather
than absent evidence; allow credible [Ne V] at the selected redshift to support
narrow-line AGN even with strong host-galaxy emission; and use `Unknown` when
the AGN identity is unresolved rather than asserting Galaxy by default.
The old QSO_4 run is retained as a pre-fix failure. The targeted real rerun
below checked the corrected prompt path once; its stability under repeated
model calls remains a WP-037 acceptance risk.
Offline verification after the edits: 80 prompt/ontology/hypothesis-label tests
passed; the plan validator and generated-view check passed. No real-model
classification result is claimed by these offline checks alone.
